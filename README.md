# IMPDS FPS Data Scraper

A Python scraper for collecting Fair Price Shop (FPS) data from the IMPDS portal.

It retrieves the data through the portal's backend requests, extracts the required information from the responses, and stores it as structured JSON for further processing.

## Approach

The initial approach was based on manually going through the website and observing the requests and responses generated by different interactions.

I initially considered using Selenium because the data appeared to be loaded dynamically through browser interactions. The approach was influenced by the general distinction between traditional and JavaScript-rendered websites, including the Selenium approach discussed in [this reference](https://scrape.do/blog/how-to-scrape-javascript-rendered-web-pages-with-python/#3-selenium-popular-solution).

However, before implementing browser automation, I started testing the individual request URLs directly.

The process was roughly:

```text
Interact with website
        ↓
Observe request
        ↓
Inspect URL, parameters and headers
        ↓
Call the URL directly
        ↓
Inspect response
        ↓
Form a hypothesis
        ↓
Test it with another request
```

This eventually showed that Selenium was not necessary. The important part was not the browser itself, but the **request sequence and session state** maintained between requests.

## Reverse Engineering the Request Flow

One of the first things discovered was that the same `stateCode` parameter is used to access different levels of the data hierarchy.

For Goa, for example:

```text
stateCode = 30
        ↓
Goa state

stateCode = 585 / 586
        ↓
North Goa / South Goa

stateCode = <FPS_ID>
        ↓
Individual FPS data
```

So despite being named `stateCode`, the parameter effectively acts as an identifier for the level of data being requested.

The request flow can therefore be represented as:

```text
Goa
 │
 ├── North Goa
 │    ├── FPS
 │    ├── FPS
 │    └── ...
 │
 └── South Goa
      ├── FPS
      ├── FPS
      └── ...
```

### Session Dependency

The next important discovery was that the requests don't all behave independently.

The district/FPS IDs can be retrieved without maintaining a client session. However, requests for the actual FPS-level data require an **established session**.

The working sequence is:

```text
Create HTTP client
        ↓
Open state page
        ↓
Request district/FPS information
        ↓
Extract FPS IDs
        ↓
Request FPS data using the same client
```

This is why the scraper uses a single `httpx.Client` for the complete district-level operation.

The problem initially looked like something that would require browser automation, but testing the individual requests showed that maintaining the correct HTTP session was the actual requirement.

## Month and Year

The selected month and year are important to the request flow.

The month and year are included in the `referer` used by the scraper:

```python
referer = f"https://impds.nic.in/sale/stateUnautmated?month={month}&year={year}"
```

During testing, requests without the expected month/year context could return:

```text
500 Internal Server Error
```

rather than the expected response.

The scraper therefore builds the request headers dynamically for the month and year being processed.

## How the Scraper Works

The main scraping flow is:

```text
Month + Year
      ↓
District
      ↓
Establish session
      ↓
Open IMPDS state page
      ↓
Request district information
      ↓
Extract FPS IDs
      ↓
Request each FPS
      ↓
Parse response
      ↓
Save as JSON
```

### 1. Establish the session

A single `httpx.Client` is created with the required headers.

The IMPDS page for the selected month and year is opened first to establish the session state.

### 2. Retrieve FPS IDs

The district endpoint is called using the same client.

The response contains FPS information, from which the FPS IDs are extracted using a regular expression.

For example:

```text
"FPSName": "12345"
```

becomes:

```text
12345
```

### 3. Retrieve FPS-level data

Each FPS ID is then passed to the FPS endpoint:

```text
fpsByCountryAjax?stateCode=<FPS_ID>
```

The same client session is used for these requests.

### 4. Parse the response

The scraper first attempts to parse the response as JSON.

If the response is not valid JSON, it is passed to the HTML parser.

For HTML responses, the parser:

1. Finds all tables.
2. Extracts table headers.
3. Extracts table rows.
4. Maps headers to row values when their lengths match.
5. Falls back to raw cleaned text if no tables are found.

The logic is therefore:

```text
Response
   ↓
JSON?
 ┌─┴─┐
Yes  No
 ↓    ↓
JSON  HTML parser
       ↓
     Tables?
      ┌─┴─┐
     Yes  No
      ↓    ↓
  Structured  Raw text
     data
```

This allows the scraper to handle both JSON and HTML responses from the portal.

## Project Structure

```text
.
├── main.py
├── scraping_service.py
├── constants.py
├── requirements.txt
├── data/
│   └── raw/
└── README.md
```

### `main.py`

The entry point of the scraper.

It loops through the configured months and districts, retrieves the FPS data, and saves the responses to the appropriate directories.

### `scraping_service.py`

Contains the scraping and response parsing logic.

Main functions:

```python
get_district_fps_data(state_code, month, year)
```

Handles the session, district request, FPS ID extraction, and FPS-level requests.

```python
parse_html_to_json(html_text)
```

Handles HTML responses and converts tables into structured Python objects.

### `constants.py`

Contains the configuration used by the scraper, including:

* Year
* Months
* Districts

### `requirements.txt`

Contains the Python dependencies required to run the project.

## Data Storage

The raw responses are organized by month and district.

```text
data/
└── raw/
    ├── 2026-01/
    │   ├── district_name/
    │   │   ├── 12345.json
    │   │   ├── 12346.json
    │   │   └── ...
    │   └── another_district/
    │       └── ...
    ├── 2026-02/
    │   └── ...
    └── ...
```

Each FPS gets its own JSON file, with the FPS ID used as the filename.

The scraper stores the responses as raw data rather than performing extensive cleaning or transformation at this stage.

## Configuration

The year, months and districts are configured in `constants.py`.

For example:

```python
YEAR = 2026

Months = {
    "January": 1,
    "February": 2,
    "March": 3
}

Districts = {
    "District Name": "district_code"
}
```

The actual values depend on the data being collected.

## Assumptions Made During Development

The initial assumption was that browser automation might be required because the website appeared to rely on dynamically triggered requests.

That assumption was later tested by inspecting and calling the individual request URLs directly.

The testing showed that:

* The relevant endpoints could be accessed directly.
* The browser itself was not required.
* The session established by the earlier requests was required for FPS-level data retrieval.
* The request context, including the month and year, was important for obtaining valid responses.

These findings led to the current `httpx`-based implementation.

## Known Limitations

### 1. Dependency on request headers and session behaviour

The scraper depends on the current request structure used by the IMPDS portal, including specific headers and session behaviour.

If the portal changes how these requests are handled, the scraper may stop working.

### 2. FPS IDs are rediscovered on every run

The scraper currently retrieves the available FPS IDs from the district endpoint every time it runs.

This means the same IDs are repeatedly discovered even when they have already been collected previously.

### 3. Sequential FPS requests

FPS data is currently retrieved one request at a time.

For districts with a large number of FPS records, this can make the overall scraping process relatively slow.

### 4. No retry mechanism

A temporary network failure, timeout, or server-side error can cause a request to fail without an automatic retry.
